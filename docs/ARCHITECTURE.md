# Architecture and security decisions

## Domain model

The database is the single source of truth. Files are linked to customers/projects and carry MIME type, size, SHA-256, uploader, category and extracted text. Financial documents use immutable numbers generated by transaction-safe yearly sequences.

## Roles

- Administrator: full configuration and approval
- Office: operational CRUD
- Project manager: project and automation approval
- Accounting: finance access and payment recording
- Technician: assigned field-work capabilities
- Read-only: view access only

The Django admin remains available for exceptional administration, while normal operation happens in the designed interface.

## Integration boundaries

Each external system is isolated behind a service adapter:

- GMX: read-only IMAP synchronization uses `BODY.PEEK`; SMTP requires an approved database draft.
- ToolTime: flexible CSV/XLSX import without destructive deletes.
- B&O: Playwright selectors live in integration configuration; filling and submitting are separate stages.
- OpenAI: backend-only Responses API calls, `store=False`, bounded project context and structured output schemas.

An integration failure does not invalidate the core project database.

## File safety

Uploads are limited to 25 MB and an allow-list of extensions. PDF/JPEG/PNG signatures are checked. PDF text extraction runs in a spawned subprocess with a timeout and output cap. All files receive a SHA-256 digest.

## Auditability

Authenticated write requests create activity records with user, route, status and source IP. Automation jobs store input, output, requestor, approver and approval timestamp.

## Availability

PostgreSQL and Redis use persistent Docker volumes and health checks. Before each deployment, the workflow creates a compressed PostgreSQL dump when a database is already running. Caddy terminates TLS and the app remains reachable over the IP during DNS setup.
